## 第 3 段：分析引擎（本地近似 GTO）

新建一个纯计算包 `packages/strategy`，不做任何读写，高级 AI 和复盘分析共用。它分四块：

1. **范围表**（`ranges`）
   - 把 169 种起手牌（例如 AKs 同花、AKo 杂色、TT 对子）各自标一个权重。
   - 范围可以用常见写法来写，比如 `TT+, AQs+, A5s-A2s`。
   - 内置的近似 GTO 翻前表按人数（单挑 / 6 人 / 9 人）和位置（UTG…BTN、SB、BB）区分，覆盖三种情况：**首个加注入池**、**面对加注**（再加注 / 跟注 / 弃牌）、**面对再加注**。
2. **对手范围推断**（`rangeModel`）
   - 翻前：按对手的动作查表。比如他在 CO 位开池，就用 CO 的开池范围。
   - 翻后：按他的动作调整范围。下注或加注就偏向强牌和听牌，再保留一部分诈唬；跟注偏向中等牌；过牌就把最强的那部分牌降权。这是简化的经验规则，在报告里会注明。
3. **胜率计算**（`equity`）
   - 用蒙特卡洛方法，算你的手牌对一个或多个对手范围的胜率，会考虑你手上的牌对对手可能组合的影响。
   - 一个局面大约算几千次。实测评估器每秒能跑上百万次，所以一个局面只要几毫秒，直接在主线程算就行，暂时不需要方案里说的 worker 线程。以后如果实测变慢再挪过去。
4. **决策评估**（`evaluateDecision`）：对你的每个决策点输出一条结果：
   - **翻前**：看你的操作在范围表里的频率。频率 ≥30% 判为合理；只是偶尔才用的混合打法判为可以更好；表里完全没有判为失误。
   - **翻后，面对下注**：算跟注、弃牌、加注各自的期望收益。跟注期望值 = 胜率 ×（底池 + 跟注额）− 跟注额；加注会额外估计对手弃牌的概率。
   - **翻后，没人下注**：比较过牌和几种下注尺度（½ 池、⅔ 池、满池）的期望收益，同样考虑对手弃牌的概率。
   - **结论**：你这一步比最优操作少赚多少个大盲。少于 0.5bb 是 🟢 合理，0.5–2bb 是 🟡 可以更好，超过 2bb 是 🔴 失误。同时给出建议操作、胜率、底池赔率、最小防守频率，以及 2–3 条理由。

**诚实地说明局限**：翻后部分没有求解器那么精确。对手范围靠的是经验规则推断，复杂局面下的结论只能作为参考。界面上会写明"近似 GTO 分析"。

## 第 4 段：大模型解说

- **怎么接**：服务端用 OpenAI 兼容接口调用。DeepSeek、通义千问、智谱都支持这种接口，切换时改环境变量就行：`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`。Key 只放在服务端，不会进前端，也不会提交到 git。
- **什么时候调用**：你点"分析"时，本地分析先算完并立刻显示；然后服务端再请求一次大模型，整手牌只调用一次。解说返回后补到页面上。结果会缓存，同一手牌再次打开不重复花钱。
- **发给模型的内容**：只有你这一手能看到的信息，也就是你的底牌、公共牌、每一步动作，加上第 3 段算出的数字和判定。**没亮出来的对手底牌绝不发送。** 提示词要求模型基于给定的数字解说，不要自己编造胜率。
- **出错怎么办**：超时 30 秒、出错或没配 Key 时，页面显示"解说暂不可用"，本地分析不受影响。返回的文字会限制长度，并过滤掉 HTML。

## Claude

有三种做法，按"换个 agent 能直接用"的程度从低到高排：

### 1. 原始对话记录（已经自动保存了）

Claude Code 把每个会话完整存在本机：

```
C:\Users\jiasu\.claude\projects\D--claudecode-card\<会话id>.jsonl
```

- **优点**：一字不漏，包括每次工具调用和输出。
- **缺点**：是 JSON 格式，非常长（这次对话有几十万字），绝大部分是命令输出。其他 agent 没法直接读进去当上下文，塞进去也会占满它的上下文窗口。适合留档，不适合导入。

### 2. 导出成可读的对话文本

我可以把这次会话导出成一个 Markdown 文件，放到项目里，比如 `docs/context/2026-11-06-session.md`。

- **优点**：人能读，任何 agent 都能打开。
- **缺点**：仍然很长，而且决策散落在对话各处。

### 3. 整理成一份上下文文件（推荐）

把这次对话里真正有用的东西浓缩成一个文件，提交到仓库里。内容包括：
- 你确认过的决策：香港部署、昵称身份、去掉 Redis、近似 GTO 加大模型解说、Drizzle + PGlite。
- 架构和各个包的分工。
- 端口和数据目录对照表，以及"一个数据目录只能一个进程"的规则。
- 开发约定：先写测试、提交信息格式、Windows 下的 Node 路径问题。
- 我自己做的取舍、暂缓的问题，以及下一步要做什么（阶段 3）。

关键是**文件名**，不同 agent 会自动读取不同的文件：

| Agent | 自动读取的文件 |
|---|---|
| Claude Code | `CLAUDE.md` |
| OpenAI Codex、Cursor 等多数工具 | `AGENTS.md` |
| Gemini CLI | `GEMINI.md` |

建议正文只写一份 `AGENTS.md`，再放一个 `CLAUDE.md`，里面只写一行 `@AGENTS.md` 来引用它，Gemini 同理。这样只维护一份内容，所有 agent 打开项目就自动知道这些上下文。提交到 GitHub 后，换台电脑、换个 agent 也都能用。

**以后导入**：
- **用支持这些文件名的 agent**：什么都不用做，在项目目录里打开就会自动加载。
- **用不支持的 agent**：开场时说一句"先读 `AGENTS.md`"，或者把内容直接粘贴进去。
- **要追溯某个细节**：再去翻第 2 种导出的完整对话。

另外，`D:\DSH\card` 那个 agent 也可以写一份它自己的 `AGENTS.md`。两边都有之后，任何一个 agent 都能快速了解两个系统各自的设计和差异，方便你对比。
