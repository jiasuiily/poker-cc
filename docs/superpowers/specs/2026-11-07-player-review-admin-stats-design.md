# 个人复盘（一键分析 + 整体评估）与管理员玩家统计 — 设计文档

日期：2026-11-07
状态：待审阅
前置：M1（账号）、M2（部署）已上线；房主开局 / 增删座位已上线（f528c9c）。本设计取代总方案 M3 中「每手自动分析、教练评估」的部分，按用户本轮的要求调整（由用户点击触发，而不是每手自动跑）。

## 1. 目标

| 用户需求 | 本设计的交付 |
|---|---|
| 管理员能看到有多少玩家登录、每人玩了多少局、玩了多久、复盘情况 | 管理页新增「玩家」区：在线人数、每人的最近活跃 / 登录次数、手数、游戏时长、红黄绿占比、整体评估记录 |
| 一个按钮分析自己所有牌局，分析过的不再分析 | 「我的」页的「一键分析」：本地分析补齐所有牌，大模型解说在后台排队逐手补上，已有的跳过 |
| 根据全部牌局分析整体情况并给出改进建议 | 「生成整体分析」：本地统计 + 漏洞归类 + 例子手牌，交给大模型写评估，并和上一次评估对比 |

成功标准：

1. 有 100 手未分析的牌时，点一键分析后 10 秒内本地分析全部完成；大模型解说在后台逐手完成，页面显示进度；再点一次不会重复调用已完成的手。
2. 服务重启打断后台任务后，再点一次只处理剩下的手。
3. 决策点不足 30 个时，整体分析提示「再多打几手」且不调用大模型；第二份评估里有「与上次相比」的对比段落和数字对照。
4. 管理员看到的手数、时长与数据库里的牌谱一致；非管理员访问管理接口得到 403。
5. 发给大模型的内容里没有任何对手未亮出的底牌（属性测试保证）。

## 2. 已确认的决策

- 一键分析包含每手的大模型解说：后台队列逐手调用，单独的每人每日上限 `LLM_BATCH_DAILY_LIMIT`（默认 200）；单手点击的解说仍用原来的每日 30 次。
- 整体评估与上一次对比；每人每天最多 3 次。
- 位置：大厅新增第三个标签「我的」（统计、趋势、一键分析、整体评估）。
- 管理员看：在线 + 登录记录 + 手数 + 时长 + 复盘统计 + 每人整体评估的文字和数字；**不**看别人的牌谱回放。
- 后台任务在现有服务进程内运行（单进程、不用 Redis 的决定不变）；重启后任务丢失，再点一次续上。

## 3. 数据

### 3.1 新列（`players`）

| 列 | 说明 |
|---|---|
| `last_login_at` timestamptz null | 每次用密码登录成功时更新 |
| `login_count` integer default 0 | 每次用密码登录成功 +1（注册算第 1 次） |
| `last_seen_at` timestamptz null | 已登录用户访问任意 API 或进入牌桌时更新，同一用户 60 秒内最多写一次（内存节流） |

「在线」= 当前连着某张牌桌，或 `last_seen_at` 在 5 分钟内。牌桌连接由 `TableRoom` 向一个进程内的 `presence` 表登记（加入 +1，离开 -1）。

### 3.2 新表 `coach_reports`

| 列 | 说明 |
|---|---|
| `id` text pk | `cr_<uuid>` |
| `player_id` text | |
| `created_at` timestamptz | |
| `status` text | `pending` / `ok` / `failed` |
| `stats` jsonb | 生成时的统计快照（见 5.1），供下一次对比和管理员查看 |
| `text` text null | 大模型输出（经 `sanitizeLlmText`，上限放宽到 4000 字） |

同一玩家同时只能有一份 `pending`（部分唯一索引 `where status = 'pending'`），以此保证双击只调用一次；`pending` 超过 120 秒视为卡住，可重新生成。

### 3.3 `llm_usage` 增加 `kind`

主键改为 `(player_id, day, kind)`，`kind` ∈ `hand`（单手点击，原有）/ `batch`（一键分析）/ `report`（整体评估）。迁移时已有行的 `kind` 填 `hand`。

### 3.4 不新增的

- 游戏时长：从 `hand_players` + `hands.started_at / ended_at` 现算（见 6.2），不存表。
- 一键分析任务：只存在内存里；进度由数据库现算（多少手已有本地分析、多少手解说是 `ok`）。

## 4. 一键分析

### 4.1 接口

- `POST /api/me/analyze-all`：开始（已在运行则直接返回当前进度）。
- `GET /api/me/analyze-all`：进度。

返回：

```json
{
  "running": true,
  "hands": 120,
  "localDone": 120,
  "llmDone": 47,
  "llmQueued": 60,
  "llmSkipped": 13,
  "reason": null
}
```

`llmSkipped` 是今天额度已满或大模型未配置而没排上的手；`reason` 为 `limit` / `disabled` / `null`。

### 4.2 流程（`apps/server/src/analysis/batch.ts`）

进程内一个 `BatchRunner`，`Map<playerId, Job>`，每人同时一个任务。

1. 找出该玩家所有牌：没有分析行，或 `engine_version` 不是当前版本的 → 逐手跑本地分析（复用 `requestAnalysis` 的本地部分，抽成 `ensureLocalAnalysis`）。每手之间 `await setImmediate`，让牌桌计时和 WebSocket 不被卡住。
2. 找出 `llm_status` 不是 `ok` 的手（按时间从新到旧）→ 逐手：先用原子认领（与单手点击同一套 `pending` 认领，避免与单手点击重复调用），再扣 `batch` 额度，再调用大模型；额度不够就停下，剩下的记为 `llmSkipped`，`reason = 'limit'`。
3. 每手调用之间不并发（一次一手）；单手失败记 `failed`，继续下一手。
4. 全部做完后任务从 Map 里移除；进度接口此时 `running: false`。

### 4.3 与现有单手分析的关系

`requestAnalysis` 拆成两步共用：`ensureLocalAnalysis(db, handId, playerId)` 和 `claimAndExplain(db, llm, handId, playerId, quota)`。单手点击用 `hand` 额度（30），批量用 `batch` 额度（200）。行为对用户不变。

## 5. 整体评估

### 5.1 统计（`packages/strategy` 里的纯函数 `summarizeDecisions`，无 IO）

输入：该玩家所有已分析的手（每手的 `decisions`、大盲、时间）。输出 `PlayerStats`：

- `hands`、`decisions`；`good` / `ok` / `mistake` 个数与占比；
- `evLossPerHand`（bb）；
- 按街：每街决策数与失误率；
- 漏洞归类（只看判定不是 `good` 的决策，按「你的动作 → 建议动作」归类）：

| 归类 | 条件 |
|---|---|
| 翻前入池过松 | 翻前，你跟注 / 加注，建议弃牌 |
| 翻前过紧 | 翻前，你弃牌，建议跟注 / 加注 |
| 跟注过宽 | 翻后，你跟注，建议弃牌 |
| 弃牌过多 | 翻后，你弃牌，建议跟注 / 加注 |
| 过于被动 | 你过牌 / 跟注，建议加注 |
| 过度激进 | 你加注，建议过牌 / 跟注 / 弃牌 |
| 下注尺度 | 你加注，建议也是加注但金额不同 |

  每类给次数和累计 EV 损失；
- `examples`：EV 损失最大的 5 个决策，带 handId、街、你的动作、建议动作、损失。

### 5.2 发给大模型的内容（`apps/server/src/coach/prompt.ts`）

- 本次 `PlayerStats`（数字）；
- 5 个例子手：只含你的底牌、当时的公共牌、你面对的下注和你的动作、建议动作与理由（从回放帧取，与单手解说相同的隐私规则）；
- 上一份 `ok` 评估的 `stats` 和 `text`（若有）。

要求输出：整体水平（一段）、最需要改进的 3 点（每点引用一个例子手）、与上次相比的变化（有上次时）。

### 5.3 接口与流程（`apps/server/src/coach/service.ts`）

- `POST /api/me/reports`：
  1. 先对没有本地分析的手补本地分析（同 4.2 第 1 步，不调大模型）；
  2. 统计；决策点 < 30 → 400「再多打几手（至少 30 个决策点）」；
  3. 插入 `pending` 行（唯一索引保证同一时间只有一份）；扣 `report` 额度（每日 3）——超了把行标 `failed` 并返回 429「今天的整体分析次数已用完」；
  4. 后台调用大模型（超时 60 秒），写回 `ok` / `failed`；
  5. 立即返回新行（`pending`），前端轮询。
- `GET /api/me/reports`：本人全部评估（新到旧）。
- 未配置大模型：返回 503「未配置大模型」，统计照常可在「我的」页看到。

## 6. 「我的」页与统计接口

### 6.1 接口

- `GET /api/me/stats?range=7d|30d|all` → `PlayerStats`（只统计已分析的手）+ `unanalyzed`（未分析手数，用于按钮文字）。
- `GET /api/me/trend?days=30` → 每天 `{ day, hands, good, ok, mistake }`（按 Asia/Shanghai 日期）。
- 参数非法返回 400。

### 6.2 游戏时长（共用函数 `playSessions`）

把一个玩家的手按开始时间排序，相邻两手间隔（上一手结束到下一手开始）小于 15 分钟的算同一段；时长 = 各段（最后一手结束 − 第一手开始）之和。

### 6.3 页面（`apps/web/src/components/Me.tsx`）

- 顶部：范围切换（7 天 / 30 天 / 全部）；手数、红黄绿个数和占比（色条）、平均每手 EV 损失、各街失误率。
- 趋势图：最近 30 天每天的红 / 黄 / 绿占比折线，纯 SVG（不引入图表库），手机竖屏可读；没有数据的天不画点。
- 一键分析：按钮显示「一键分析（N 手待分析）」；运行时显示两条进度（本地 X/Y、解说 X/Y）和额度提示；每 2 秒轮询，离开页面停止轮询。
- 整体分析：「生成整体分析」按钮（显示今日剩余次数）；最新一份完整显示，旁边是与上一份的数字对照（例如「失误率 18% → 12%」）；更早的折叠在下面。

## 7. 管理员「玩家」区

### 7.1 接口

- `GET /api/admin/players` → 汇总 `{ total, onlineNow, active7d }` + 每人一行：
  `id, displayName, username, online, lastSeenAt, lastLoginAt, loginCount, hands, playSeconds, analyzedHands, good, ok, mistake, evLossPerHand, reports`。
- `GET /api/admin/players/:id/reports` → 该玩家的整体评估（文字 + 统计快照）。
- 都要求管理员（`requireAdmin`），否则 403。

### 7.2 页面（`Admin.tsx` 新增一节）

汇总三个数字；下面一张表（手机上横向滚动），点某行展开该玩家的整体评估列表。

## 8. 隐私

- 一键分析和整体评估只用该玩家本人的决策；例子手只含他当时能看到的信息（底牌只有自己的，公共牌按当时的街截断）。
- 管理员只看统计数字和整体评估文字，不提供别人的回放或单手分析接口。
- 属性测试：随机牌局 → 构造整体评估提示词 → 断言不含任何对手未亮出的底牌。

## 9. 测试

- `summarizeDecisions`：手工构造的决策 → 各归类计数、占比、例子排序正确。
- `playSessions`：间隔 14 / 16 分钟的边界；单手；跨天。
- 一键分析：已有 `ok` 解说的手不再调用；`batch` 额度到上限后停止并报告 `limit`；同一玩家并发两次只有一个任务；模拟中途中断后再运行只处理剩下的；与单手点击同时进行时同一手只调用一次。
- 整体评估：< 30 决策点返回 400 且不调用；第二份的提示词包含上一份的统计；每日第 4 次返回 429；双击只有一份 `pending`；`pending` 超时后可重来。
- 登录记录：登录成功 `login_count + 1`、失败不变；`last_seen_at` 节流。
- 管理接口：非管理员 403；手数、时长与构造数据一致。
- 隐私属性测试（见第 8 节）。
- 前端：预览实例（2575 / 5175）跑通：打几手 → 一键分析看进度 → 生成整体分析 → 管理页看玩家。

## 10. 不在本次范围

- 每手结束自动分析（总方案 M3 原设想）：本轮按用户要求改为手动一键。
- 分析放进 worker 线程：先用「每手之间让出事件循环」；若实测牌桌卡顿再改。
- 按位置的失误统计：牌谱里有座位和按钮，但位置换算放到以后。
- 管理员查看别人的牌谱回放。
